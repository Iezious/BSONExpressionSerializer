# Decisions — 001.known-defects (fixes for the reviewed known defects, BSONExpressionSerializer)

Fixes for the known defects D1–D9 that the review of the pre-existing system recorded in `000.legacy.md`. Each entry supersedes the defect it fixes in a legacy entry; the legacy entry keeps its text and its status names the entry that replaces it. The regression tests are `test/BSONExpressionSerializerTests/PostReviewTests.fs`, one section per defect, which also carries the verbatim defect description. Branch `fix/known-defects`.

### DEC-001-1 — Two members mapped to one stored name are refused when the serializer is created
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** coder (confirmed: user)
- **Question:** What happens to a type in which two members map to the same stored name? (defect D1)
- **Decision:** The writer's build groups the type's stored members (public instance properties not marked `BsonIgnore`) by stored name (DEC-000-28) and throws `InvalidOperationException` when a name has more than one member. The message names the type, the stored name and the members: `Type '<full name>' maps more than one member to the same stored name: '<name>' <- A, B`. A property name that equals another member's `BsonElement` name is a clash; an excluded member is not. The check runs wherever the writer is built, so a clash in a nested type, an array element type or a dictionary value type also refuses the registration. Registration builds the writer, so the type is refused when the serializer is created (DEC-000-3), not on every whole-document write with "Duplicate element name". A stand-alone reader alone does not check.
- **Reason:** A type the library cannot store is refused when the service starts, which is the rule DEC-000-3 records for every other unbuildable type.
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:281-305`
- **Cites:** `../architecture/overview.md` § Failure model; US-005.AC-3; supersedes the duplicate-name defect of DEC-000-3

### DEC-001-2 — A stored null text reads as null at any depth; text with no value is still written as null
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** user
- **Question:** How does a text member with no value round-trip? (defect D2)
- **Decision:** Read: text goes through the same null guard as binary, arrays and dictionaries, so a stored null loads as null in a top-level member, a nested type, an array element and a dictionary value. Write: unchanged. Text with no value and no omit choice is stored as an explicit null; with "omit when null" or "omit when default" it is left out (DEC-000-17). A missing text field loads as null, as before, which the tests now guard for every reference and optional kind at the top level, in nested types and in array elements.
- **Reason:** The library must read back every document it writes, and documents stored before a field was added must still load. Writing an explicit null when no omit choice is set is acceptable. `[confirmed: user]`
- **Rejected:** Leaving a null text out of the document without an omit choice. Omission stays a per-field choice. `[confirmed: user]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:152-159`
- **Cites:** `../architecture/interfaces.md` § Read rules; US-004.AC-3; supersedes the text half of DEC-000-15

### DEC-001-3 — A binary member with no value is stored as an explicit null at any depth
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** coder (confirmed: user)
- **Question:** How is a binary member with no value and no omit choice stored? (defect D3)
- **Decision:** The writer routes a byte array through the same null check as text, so a null is stored as BSON null instead of failing with "Value cannot be null. (Parameter 'bytes')". This also covers a null element of an array of byte arrays and a null dictionary value, which no attribute can omit. The reader's existing guard (since b09139e, DEC-000-15) loads it back as null. With "omit when null" or "omit when default" the member is left out, as before.
- **Reason:** Same rule as text (DEC-001-2): a member with no value is stored as null unless an omit choice is set.
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:187-195`
- **Cites:** `../architecture/interfaces.md` § Write rules; US-004.AC-4, AC-5; supersedes the binary half of DEC-000-15

### DEC-001-4 — The omission attributes' on/off argument is read; switched off, the attribute has no effect
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** coder (confirmed: user); the `BsonIgnoreIfNull` half: user
- **Question:** What does `BsonIgnoreIfDefault(false)` or `BsonIgnoreIfNull(false)` do? (defect D4)
- **Decision:** Each attribute counts only when its `Value` is true. Switched off, the member behaves as if the attribute were absent, and the remaining rules of DEC-000-17 apply: an option or value option is left out when empty, anything else is written. Consequence for DEC-000-3: "omit when null" on a member that cannot hold null, and "omit when default" on a value option, are refused at creation only when switched on; switched off, both are accepted. The `BsonIgnoreIfNull` case was not in the defect list; it was found while fixing D4 and fixed on the user's request.
- **Reason:** An attribute switched off must not act. The store's own default mapping reads the same argument.
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:252-268`
- **Cites:** `../architecture/interfaces.md` § Write rules, § Mapping attributes; US-007.AC-4, AC-6; supersedes the on/off defect of DEC-000-17 and the `BsonIgnoreIfNull` on/off limit of DEC-000-25; narrows the omission refusals of DEC-000-3

### DEC-001-5 — An enumeration inside an option, value option, nullable or array is translated in the field's declared form
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** coder (confirmed: user)
- **Question:** In which form do typed filters and updates translate an enumeration held in a wrapper or an array? (defect D5)
- **Decision:** The member resolver builds the inner enumeration serializer from the member's `BsonRepresentation`, or the 32-bit number form when none is declared: the store's enumeration serializer in that representation. A nullable wraps it in the store's nullable serializer (the binding DEC-000-29 records is kept); an option or value option wraps it in the library's wrapper; an array of enumerations gets the store's array serializer around it. Any other inner or element type still comes from the registry. A by-name filter now matches, and an update stores the name, so the record still loads. A dictionary's values are not covered; a dictionary member still goes through the registry.
- **Reason:** Translation must produce the form whole-document storage writes (DEC-000-19).
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionDocumentSerializer.fs:38-57,76-120`
- **Cites:** `../architecture/interfaces.md` § Typed filters and updates; US-009.AC-7, US-010.AC-5; supersedes the wrapped-enumeration defect of DEC-000-29

### DEC-001-6 — Typed filters, updates and sorts target the stored name; an excluded member gets no member answer
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** coder (confirmed: user)
- **Question:** Which document field does a typed filter, update or sort target, and what happens for an excluded member? (defect D6)
- **Decision:** Every member answer carries the stored name, on the first resolution and on cached answers alike. The name comes from the writer's own stored-name function (`ExpressionWriter.getNameInBson`, made `internal`), so storage and translation share one rule (DEC-000-28): the `BsonElement` name, or the property name when none or a blank one is given. A `BsonIgnore` member gets no answer, so the store refuses a filter, update or sort on it when the query is built. Effects a consumer can see: before this fix, a typed update on a renamed field wrote under the property name, a field the reader never loads (unknown fields are skipped, DEC-000-13); documents that hold such a field keep it, and cleaning them is a data task outside the library. A filter or sort on an excluded member used to match nothing and now fails.
- **Reason:** A typed filter or update must address the field whole-document storage writes, and an excluded member has no stored form to address.
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:14-16`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionDocumentSerializer.fs:148-167`
- **Cites:** `../architecture/interfaces.md` § Typed filters and updates; US-009.AC-6, US-010.AC-3, AC-4; supersedes DEC-000-30

### DEC-001-7 — Member answers are cached in a concurrent map filled with get-or-add
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** coder (confirmed: user)
- **Question:** How is the member cache kept safe when requests first use members of a type at the same moment? (defect D7)
- **Decision:** The per-serializer cache is a `ConcurrentDictionary` from member name to serializer, filled with `GetOrAdd`. There is no lock. Racing threads may each build a serializer for a member, but only the first one stored is kept, and every thread answers with it, so all answers for a member are the same instance. A race can no longer fail a request or leave the map broken.
- **Reason:** One registered instance serves every request in the process, and the store asks it on the request thread.
- **Rejected:** A lock around resolution. Not needed: building a member serializer twice is harmless, and the get-or-add keeps one.
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionDocumentSerializer.fs:20-27`, and every `GetOrAdd` in the same file
- **Cites:** `../architecture/overview.md` § Failure model; US-009.AC-8, US-010.AC-6; supersedes DEC-000-33

### DEC-001-8 — The optional-value wrappers consume a stored null
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** coder (confirmed: user)
- **Question:** How does a member wrapper read a stored null when the store reads that member on its own? (defect D8)
- **Decision:** On a null, each wrapper (`OptionSerializer`, `ValueOptionSerializer`, `NullableSerializer`) reads the null before returning the empty value, so the reader moves past it like any other serializer. A projection of one member, distinct on it, and every other path that reads a member and goes on now succeed. The untyped read of the value-option wrapper returns an empty value typed as `'t voption`; it used to be inferred as `ValueOption<obj>`, so a caller casting it failed. The option wrapper's empty value is typed the same way, though `None` was harmless. The library's own `NullableSerializer` had the same defect and is fixed too, although the library still does not use it (DEC-000-37).
- **Reason:** A serializer must leave the reader after the value it read.
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/HelperSerializers.fs:7-97`
- **Cites:** `../architecture/interfaces.md` § Typed filters and updates; US-004.AC-8, AC-9; supersedes DEC-000-35

### DEC-001-10 — Every workflow installs the .NET 10 SDK before building
- **Status:** accepted
- **Stage:** — · **Feature:** 001.known-defects · **Step:** —
- **Date:** 2026-11-17 · **Decided by:** user
- **Question:** Which SDK do the build, release and preview workflows build with? (found while fixing D9)
- **Decision:** Each workflow runs `actions/setup-dotnet@v4` with `dotnet-version: 10.0.x` right after checkout, so the job builds with the newest .NET 10 SDK whatever the runner image preinstalls. Checkout moves from `actions/checkout@v2`, which runs on a retired Node version, to `@v4`. The build, test, pack and push commands are unchanged. Checked by running each workflow's commands in the `mcr.microsoft.com/dotnet/sdk:10.0` Linux image on a clean export of the repository, including on 2 CPUs like a standard runner: build and test pass, and the release and preview packs produce `Iezious.Libs.BSONExpressionSerializer.<version>.nupkg`.
- **Reason:** The library and its tests target net10.0 (DEC-000-40); a runner image without that SDK would fail every build and every release.
- **Rejected:** A `global.json` pinning an exact SDK. Not needed: the feature band follows the target generation, and a pin would have to be bumped with every SDK patch.
- **Lands in:** `.github/workflows/build.yml`; `.github/workflows/release.yml`; `.github/workflows/preview.yml`
- **Cites:** `../architecture/overview.md` § Distribution; DEC-000-40; DEC-000-44; DEC-001-9
