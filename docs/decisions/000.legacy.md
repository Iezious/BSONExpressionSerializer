# Decisions — 000.legacy (pre-existing system, BSONExpressionSerializer)

Technical choices found in the code when it was documented. A later feature supersedes an entry by writing a new one and flipping this one's status; nothing is deleted or renumbered.

### DEC-000-1 — Reader and writer are compiled once per type when the serializer is created; the stand-alone builders compile on every call
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-04-12 · **Decided by:** observed (confirmed: user)
- **Question:** When are a type's reader and writer built, and how often?
- **Decision:** The document serializer's constructor builds one expression tree over the type. It compiles one document→value delegate and one value→document delegate, and every whole-document read or write calls them. The stand-alone builders `CreateReader` and `CreateWriter` compile a new delegate on each call, with no cache; the caller keeps the result. History: v1.0.1–1.0.7 shipped only the stand-alone builders (e256d23 and 72ad03c, 2022-02-17); 977f4bd (2022-04-12, v1.0.8) added the serializer as a thin wrapper around them.
- **Reason:** Compiling from the type supports F# optional values and tolerant loading. `[confirmed: user]` It also turns each document conversion into a single delegate call. `[inferred]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionDocumentSerializer.fs:16-17`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:233-237`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:283-287`
- **Cites:** `../architecture/overview.md` § Components, § Call structure; US-011; US-012

### DEC-000-2 — The build reads the type alone; the store's class map and registered conventions are never consulted
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-04-12 · **Decided by:** observed (confirmed: user)
- **Question:** Where do the reader and writer take per-field choices from: the stored name, exclusion, omission, default and enumeration form?
- **Decision:** Every choice comes from attributes on the property itself. The store's default mapping for the type is never consulted. Neither is any convention a service registers. So a store-wide convention, such as enumerations by name, never reaches a registered type.
- **Reason:** The reader and writer are compiled from the type alone, once, at registration (DEC-000-1). As a result, registered conventions never reach them. `[confirmed: user]`
- **Rejected:** Not recorded in the library. On the shared-model side, a convention was rejected because "the shared serializer ignores it" (SinSystems.Models/DEC-000-10).
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionDocumentSerializer.fs:21-27`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:15,25,204,219`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:15,21,45,242-243,263`
- **Cites:** `../architecture/interfaces.md` § Mapping attributes, § Registration contract; UC-011 A2; US-011.AC-6; SinSystems.Models/DEC-000-10

### DEC-000-3 — An unbuildable type, or an unsupported combination of field choices, fails when the serializer is created
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-04-12 · **Decided by:** observed (confirmed: user)
- **Question:** When does a type the library cannot handle fail: at registration or at its first store?
- **Decision:** The build is eager, with no lazy build and no per-member fallback. On the registered path, the serializer is created at consumer start-up. The library has no validation of its own; each failure below is a side effect of building the expression tree: an unsupported member kind (see DEC-000-5); a computed member that is not excluded, "Expression must be writeable"; "omit when null" on a member that cannot hold null, including inside nested types and array element types, "Argument types do not match"; "omit when default" on a value option, the binary operator Equal is not defined; a declared default that cannot be converted to the member type, "No coercion operator is defined". Known limit (confirmed: user): "omit when null" on a member that cannot hold null, and "omit when default" on a value option, are refused when the serializer is created. Known limit (confirmed: user): the messages name neither the member nor, in most cases, the type. Known defect (confirmed: user): two members mapped to one stored name pass creation, and every whole-document write of that type then fails with "Duplicate element name"; intended behaviour: US-005.AC-3.
- **Reason:** A type the library cannot handle is refused when the service starts, not at its first store. `[confirmed: user]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionDocumentSerializer.fs:16-17`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:224-233`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:205-206`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:272,276`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:224`
- **Cites:** `../architecture/overview.md` § Failure model; `../architecture/interfaces.md` § Registration contract; UC-011 E3, E4; US-011.AC-5; UC-007 E1; US-005.AC-3

### DEC-000-4 — Registration has no library helper, guard or idempotence
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-04-12 · **Decided by:** observed (confirmed: user)
- **Question:** How does a service register a type, and what happens on a second or late registration?
- **Decision:** The service creates the serializer itself and hands it to the store's process-wide registry. The serializer's constructor takes no arguments. The library offers no helper, no "already registered" check and no idempotent registration. The store refuses a second registration of the same type. It also refuses a registration that comes after it has already resolved the type with its default handling, which happens when a typed filter reached the type, a collection was opened, or a value was stored. History: 977f4bd (2022-04-12); the first consumer registrations followed the same day.
- **Reason:** The duplicate and late refusals are the store's own rules. Why the library adds no guard of its own is not recorded. `[confirmed: user]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionDocumentSerializer.fs:12`
- **Cites:** `../architecture/interfaces.md` § Registration contract; UC-011 E1, E2; US-011.AC-3, AC-4

### DEC-000-5 — Nested types are compiled inline, and every unmatched member type is treated as a nested type
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-02-17 · **Decided by:** observed (confirmed: user)
- **Question:** How is a member whose type is another data type converted, and does it need its own registration?
- **Decision:** A member type outside the handled families goes to a nested-type branch. That branch builds a sub-reader and a sub-writer into the containing type's delegates, recursively. Array elements and dictionary values go through the same dispatch. The branch consults neither the store's registry nor the library's override registry, so a nested type converts the same way whether or not it is registered; its own registry entry stays the store's default handling. The branch is also how unsupported kinds are refused, as a side effect of building them: value types, "Argument types do not match"; get-only properties, "Expression must be writeable"; no parameterless constructor, "does not have a default constructor". Known limit (confirmed: user): an `obj` member is accepted and stored as an empty sub-document, so its value is lost. Known limit (confirmed: user): there is no cycle guard; a self-referencing type overflows the stack while its serializer is created, which ends the process. Known limit (confirmed: user): a nested value stored on its own follows this form only if its type is registered too; an example is a hand-built change that embeds the value. History: 7843263 (2022-02-17, "Subobjects tested"); 4bdf3c6 (2022-02-18, "nested classes tested").
- **Reason:** A nested type is part of its parent's stored form, so it needs no registration of its own. `[confirmed: user]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:189-198`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:210-220`
- **Cites:** `../architecture/interfaces.md` § Registration contract, § Stored form, by type family; `../architecture/overview.md` § Failure model; US-001.AC-3; UC-001 E2; UC-011 E5, E6

### DEC-000-6 — A type maps its public instance properties; static members are skipped
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-04-24 · **Decided by:** observed (confirmed: user)
- **Question:** Which members of a type become document fields?
- **Decision:** Both directions map the public instance properties, less those marked `BsonIgnore`. The reader creates the object with its parameterless constructor and then assigns every mapped property, from the stored value or the default. So each mapped property must be settable, and a computed member must be excluded. Public fields that are not properties are not mapped. History: 35be70b (2022-04-24, "Ignore static props"), merged as 920378d (PR #7) and released as v1.0.9.
- **Reason:** Consumer projection types carry a static projection description. Mapping it as a field broke their registration. `[confirmed: user]`
- **Rejected:** Calling `GetProperties()` without binding flags. That included static properties (diff of 35be70b).
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:217-226`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:263`

### DEC-000-7 — A closed list of supported member kinds, mirrored in reader and writer; arrays and text-keyed dictionaries are the only collections
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-02-17 · **Decided by:** observed (confirmed: user)
- **Question:** Which member kinds does the library convert, and what happens to the others?
- **Decision:** The reader and the writer each have one fixed match over the same supported families: `string`, `bool`, `Int32`, `Int64`, `Guid` (see DEC-000-8), `float`, `Decimal`, `Decimal128`, `DateTime`, `BsonObjectId`, `ObjectId`, `BsonDocument`, `byte[]`, enumerations, `Nullable<_>`, `Option<_>`, `ValueOption<_>`, one-dimensional arrays and `Dictionary` with text keys. The only collections are one-dimensional arrays and `Dictionary` with text keys. Any other member type goes to the nested-type branch (DEC-000-5), so lists, sequences, F# maps and other dictionary types fail at creation there. A multi-dimensional array, or a `Dictionary` keyed by anything but text, is taken by the array or dictionary branch instead, and that branch fails at creation. The library has no refusal code of its own. History: reader list e256d23 and writer list 72ad03c, both 2022-02-17; Double and widening came in e971e2a; the raw-document branch in 12a38fa and a935a7e (2022-02-18); no source change since v1.0.11.
- **Reason:** The list is closed on purpose. `[confirmed: user]` It covers the kinds the shared models and consumer projections use. `[inferred]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:64-139,150-198`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:89-158,175-220`
- **Cites:** `../architecture/interfaces.md` § Stored form, by type family; UC-001 E1; US-011.AC-5

### DEC-000-8 — Guid is listed but refused since the move to BSON 3.x
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2026-05-27 · **Decided by:** observed (confirmed: user)
- **Question:** Is a Guid member supported?
- **Decision:** The Guid branch is still in the reader and the writer, but it relied on implicit conversions that BSON 3.x removed. Since v1.0.12 (3b7a15f), a type with a Guid member fails at creation. On the 2.x line (v1.0.11 and earlier), a Guid was stored as legacy binary subtype 3, which the current reader cannot read. Known limit (confirmed: user): Guid is unsupported on the current line. No test has ever covered Guid.
- **Reason:** The loss came with the dependency upgrade and was not known at the time. It is accepted as unsupported. `[confirmed: user]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:161`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:188`; `src/Iezious.Libs.BSONExpressionSerializer/Iezious.Libs.BSONExpressionSerializer.fsproj:12`

### DEC-000-9 — Whole-document reads and writes go through an in-memory document
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-04-12 · **Decided by:** observed (confirmed: user)
- **Question:** How does the registered path convert between the store's byte stream and a value?
- **Decision:** On read, the serializer reads the whole document into an in-memory document and then calls the compiled reader. On write, it builds an in-memory document with the compiled writer and then writes that document out. There is no streaming conversion.
- **Reason:** The same compiled converters serve both the registered path and the stand-alone path, so the stored form is identical on both. `[confirmed: user]` Random access by field name also keeps the missing-field and unknown-field rules simple. `[inferred]`
- **Rejected:** Deriving the serializer from the BSON library's document serializer: an `inherit` line was added already commented out in 62d727e (2023-07-04), and no reason is recorded. A streaming reader: see DEC-000-10.
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionDocumentSerializer.fs:21-27`
- **Cites:** `../architecture/overview.md` § Call structure; US-012.AC-1, AC-2

### DEC-000-12 — One field-default definition, converted to the member type at build time and mirrored in reader and writer
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-02-17 · **Decided by:** observed (confirmed: user)
- **Question:** Which value does a missing field load with, and which value does "omit when default" compare against?
- **Decision:** Both sides choose in the same order: (1) the `BsonDefaultValue` value, converted to the property type; (2) otherwise, empty for an option or value option; (3) otherwise, the type default: 0, false, or null for reference kinds. The declared value becomes a typed constant when the type is built; standard numeric conversion applies, so a whole-number literal works on 64-bit and fractional members, and an unconvertible default fails creation (DEC-000-3). The reader's copy and the writer's copy are kept in step. History: 5ea0fb4 (reader: declared default and empty option) and 72ad03c (writer), both 2022-02-17.
- **Reason:** The writer's default is the reader's: one definition, mirrored. `[confirmed: user]` A service can read documents written before a field existed without migrating them. `[inferred]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:203-211`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:20-28`
- **Cites:** `../architecture/interfaces.md` § Read rules, § Write rules; UC-003; US-003.AC-1, AC-2, AC-3; US-007.AC-3

### DEC-000-14 — A stored null loads as empty for optional and reference kinds, fails for value kinds, and never takes the declared default
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-02-18 · **Decided by:** observed (confirmed: user)
- **Question:** What does a field stored as null load as?
- **Decision:** Kinds that load a stored null as empty: option and value option, which read null as empty; nullable, arrays, dictionaries, nested types, byte arrays and raw documents, which are guarded against null. Kinds that fail on a stored null: bool, the number kinds, decimal, date, object id and enumeration; they read the stored value directly, so the load fails. The declared default is assigned only when the field is absent; a stored null is never replaced by the default. Text is covered by DEC-000-15. History: e89cd15 (generic nullable read) and 3372676 (null guard for arrays and dictionaries), both 2022-02-18.
- **Reason:** An empty value in a non-optional number, flag or date field fails that load. `[confirmed: user]` The default fills only a missing field. `[confirmed: user]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:43-46,49-62,141-148,150-198,219-226`
- **Cites:** `../architecture/interfaces.md` § Read rules; `../architecture/overview.md` § Failure model; UC-004 E1; US-004.AC-6, AC-7

### DEC-000-15 — Null text is written as null but read without a guard; null binary is read with a guard but written without one
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-02-18 · **Decided by:** observed (confirmed: user)
- **Question:** How are a text member and a binary member with no value stored and loaded?
- **Decision:** Text, write: a text member with no value is written as an explicit null, and the field stays in the document (guard added in 972008e and 3372676, 2022-02-18). Text, read: there is no null guard; a stored null fails with "Unable to cast object of type 'MongoDB.Bson.BsonNull' to type 'MongoDB.Bson.BsonString'", at any depth: in a nested type, an array element or a dictionary value. Known defect (confirmed: user): the library writes a document it cannot read back; intended behaviour: US-004.AC-3. Binary, read: guarded since b09139e (2022-02-18, released in v1.0.6); a stored null loads empty. Binary, write: no guard; storing a binary member with no value fails with "Value cannot be null. (Parameter 'bytes')", and the same failure happens for a null element in an array of byte arrays. Known defect (confirmed: user): a binary member with no value and no omit choice cannot be stored; intended behaviour: US-004.AC-4. With "omit when null" or "omit when default", both kinds round-trip as empty (DEC-000-17). The exposure is live (confirmed: user): one consumer path stores records with null text, and readers that use registration fail on them.
- **Reason:** The text read and the binary write were oversights: the binary read guard fixed an edge case found in testing, and the binary write was never revisited because its only test used a fixture marked to omit nulls. `[confirmed: user]` The guards were added kind by kind, as tests exercised each kind. `[inferred]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:175-185`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:152,175-176`
- **Cites:** `../architecture/interfaces.md` § Read rules, § Write rules; `../architecture/overview.md` § Failure model; UC-004; US-004.AC-3, AC-4, AC-5

### DEC-000-17 — Omission rules: which rule applies and in what order; the omission attribute's on/off argument is not read
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-02-18 · **Decided by:** observed (confirmed: user)
- **Question:** When is a member left out of the stored document?
- **Decision:** The first matching rule wins: (1) both markers: left out when null or equal to the default; (2) "omit when default": left out when equal to the default (DEC-000-12, DEC-000-18); (3) "omit when null": left out when null; (4) an option or value option: left out when empty; (5) anything else: always written. A marker overrides the optional kind's own rule. The check wraps the add, so the value of a left-out member is never evaluated. Known defect (confirmed: user): the attribute's on/off argument is never read, so "omit when default" switched off still leaves the member out; intended behaviour: US-007.AC-4. History: 72ad03c (default marker only), e89cd15 (option and value option split), e091472 (2022-02-18, "The support of default null was added": null marker and combined check).
- **Reason:** Per-field omission is the library's per-field control. `[confirmed: user]` The markers were added ahead of the kind rules in e091472. `[inferred]`
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:224-256,263-278`
- **Cites:** `../architecture/interfaces.md` § Write rules, § Mapping attributes; UC-007; US-007.AC-1, AC-2, AC-4, AC-5

### DEC-000-18 — "Equal to the default" uses the expression library's Equal
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-02-17 · **Decided by:** observed (confirmed: user)
- **Question:** How does "omit when default" decide that a value equals the default?

### DEC-000-19 — An enumeration's storage form is declared on the field, applies to every value the field holds, and defaults to a number
- **Status:** accepted
- **Stage:** legacy · **Feature:** 000.legacy · **Step:** —
- **Date:** 2022-02-22 · **Decided by:** observed (confirmed: user)
- **Question:** Where does an enumeration's storage form come from, and what does it cover?
- **Decision:** The form is read from the field's representation attribute, never from the enumeration type. It governs the enumeration everywhere in that field: inside arrays, options, value options and nullables. Without the attribute, the value is stored as a 32-bit number. Int64 gives the 64-bit form (DEC-000-21). String gives the name. History: e256d23 and 72ad03c, 2022-02-17; 75097b6 (2022-02-22, PR #6 "bugfix/enum_voption_fails", v1.0.7): the name is now taken from the enumeration type instead of its wrapper.
- **Reason:** Numbers are the default. `[confirmed: user]` The form is chosen per field because service-wide conventions do not reach registered types (DEC-000-2). `[confirmed: user]`
- **Rejected:** A by-name convention, whether built into the library or registered by a service (SinSystems.Models/DEC-000-10).
- **Lands in:** `src/Iezious.Libs.BSONExpressionSerializer/ExpressionReader.fs:24-35`; `src/Iezious.Libs.BSONExpressionSerializer/ExpressionWriter.fs:44-57`

### DEC-000-21 — The 64-bit enumeration form is written through a 32-bit integer
